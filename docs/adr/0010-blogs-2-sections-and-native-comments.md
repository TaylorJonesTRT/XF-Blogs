# Blogs 2.0: Blog Sections in the node tree, native comments

Blogs today live outside XenForo's node tree, at `/blogs/`, with global permissions and comments stored as forum threads (ADR 0001). For 2.0.0 we will add a custom node type, the **Blog Section**, which holds member Blogs (Node → Blog Section → Blog → Blog Post), and replace Discussion Threads with a native comment content type. This follows digitalpoint's Marketplace approach: purpose-built content under a custom node type, not threads under a forum type. It ships in the same add-on as a hard cutover, so there's one permission model and one comment system afterwards.

## Decisions

1. **Same add-on, hard cutover.** Every Blog gets a required `node_id`. The upgrade creates one default Blog Section (at the root, placed last, `display_in_list = 0`, titled "Blogs") and assigns every existing Blog to it.
2. **Blog Section, not "Blog".** Blogs are member-owned and a member can own several (`blogCreationLimit`), so a node per Blog could mean thousands of nodes. The node is a container, and "Blog" keeps its glossary meaning. The node type id is `TaylorJBlogsSection`.
3. **Assignment.** "Create blog" lives on the Blog Section page and is gated by that section's node permission, the same way "Post thread" works in a forum. Moving a Blog to another section is a moderator action. Authors can't move their own Blogs.
4. **Permissions.** A node type has exactly one `permission_group_id`, and `NodePermissions::getFinalPerms()` only builds that group. So we add one new group, `taylorjBlogSection`, that holds every view, create, post, edit, delete, moderate, tag, approve and comment permission. IDs must not collide (the current `taylorjBlogs` and `taylorjBlogPost` groups both define `canEditAny`, `canDeleteAny`, `canHardDeleteAny` and `canUndeleteAny`). Global values act as defaults and each section can override them. `blogCreationLimit` stays in a group that is only global. The upgrade copies `xf_permission_entry` rows from the old IDs to the new ones, and approval stops borrowing `forum.approveUnapprove`.
5. **Section settings** go on the node edit form: moderate new blogs, moderate new blog posts, allow comments, moderate new comments, and count comments toward `message_count`. The upgrade seeds the default section from `taylorjBlogsBlogApproval`, `taylorjBlogsBlogPostApproval` and `taylorjBlogsBlogPostComments`, then those options are removed. Paging, title length and minimum tags stay global. The unused options `taylorjBlogsBlogLimit` and `taylorjBlogsBlogPostOther`, and the comment-forum and delete-thread-action options, are removed.
6. **Native comments replace Discussion Threads.** This supersedes ADR 0001 once 2.0 ships. Comments are flat and work like XenForo messages: BBCode, quote and multi-quote, editing with edit history, soft and hard delete, approval queue, reactions, reports, alerts, attachments, search and inline moderation.
7. **Existing comments are converted** by a batched, resumable job enqueued from `postUpgrade()`. Each Discussion Thread reply becomes a comment; the auto-generated first post is skipped. Reactions, attachments, edit history, reports, IPs, approval queue and deletion log entries are re-keyed through a mapping table from `post_id` to `comment_id`.
8. **The original threads are soft-deleted** after conversion. Their `discussion_type` is reset first, so the `blogPost` thread type and the `XF\ForumType\Discussion` extension can be removed.
9. **Comments count toward `message_count`**, with a per-section toggle that defaults to on. Soft-deleting a thread lowers its authors' counts, and conversion adds them back.
10. **Blog Post Watch.** This is a new watch type that works like a thread watch: members are auto-watched when they write a post or comment, and are notified of new comments. Conversion turns `xf_thread_watch` rows on Discussion Threads into Blog Post Watches. Blog Watch doesn't change. A watch for a whole section is deferred.
11. **URLs use names, not IDs.** Sections are at `/blogs/<section>/`, Blogs at `/blogs/<blog>/`, and posts at `/blogs/<blog>/<post>/` (for example `/blogs/johns-garage/rebuilding-a-carb/`). Each Blog gets a unique `blog_name` handle, chosen when it's created, with the same character rules as `node_name`. Section `node_name`s and Blog handles share the first URL segment, so each is checked against the other and against reserved words (`post`, `blog`, `authors`, `add`, `page-N`). Each post gets a slug that is unique within its Blog and fixed when the post is first published. If a slug is changed later, a slug-redirect table 301s the old URL. A catch-all route under `blogs/` resolves the path as a section, then a Blog, then a post, and route build callbacks generate the links. The existing `blogs/post/…` and `blogs/blog/…` sub-routes stay as permanent redirects: their literal prefixes match before the catch-all, so links already stored in alerts and thread posts keep working. Admins can rename the `blogs/` prefix with XenForo route filters. `/blogs/` becomes a landing page: it redirects to the only section the visitor can view, and otherwise lists sections and the latest posts. The nav tab stays.
12. **Releases.** 1.8.x is the last 1.x line. It fixes the live bugs that are cheap to fix and adds an ACP notice that describes the 2.0 changes. A `1.x` branch is kept for security fixes. The next release after that is 2.0.0 Beta 1 (`2000031`), and Blog Sections and native comments ship together in it.

## Considered options

- **Custom forum type plus thread type (like Article), with replies as comments.** Rejected: a blog post isn't a thread, and this would push blogs further into the forum hierarchy rather than giving them their own. When we revisited it, we found it would give us forum node permissions for free, which would make Decision 4 unnecessary. It still loses for two reasons. First, the Blog has no natural home: it would have to be a forum node (rejected above) or a sidecar row on every thread. Second, threads only have `visible`, `moderated` and `deleted` states, so drafts and scheduled posts would need their own storage outside the thread.
- **A node per Blog.** Rejected because Blogs are per-member, and thousands of nodes slow down nested-set rebuilds, node permissions and the node list.
- **Additive nodes, with `node_id = 0` allowed** (the earlier `.agents/plans/reflective-gathering-thunder.md`). Rejected because global permissions would apply to Blogs with no section and node permissions to the rest, permanently.
- **Keep threads as storage and show the replies under the post.** Rejected because it keeps the forum dependency and the per-section comment-forum setup.
- **Keep the old Discussion Threads and use native comments only for new posts.** Rejected because it means two comment systems with no end date.
- **Ship Sections in 2.0 and comments in 2.1.** Rejected in favour of a single cutover.
- **Leave the original threads closed instead of soft-deleting them.** Rejected because the converted text would be duplicated in search and in the forum.
- **URLs in XenForo's default `title.id` style** (`/blogs/<section>/`, `/blogs/blog/<title>.<id>/`, `/blogs/post/<title>.<id>/`). Rejected: the `blog/` and `post/` segments add nothing to the URL, and post URLs don't show which Blog they belong to.
- **Blog handles with the ID kept on posts** (`/blogs/<blog>/<post-title>.<id>/`). This is about half the work: lookup is by ID, so post slugs and the redirect table aren't needed. Rejected in favour of URLs without IDs.
- **Fully nested URLs** (`/blogs/<section>/<blog>/<post>/`). Rejected: every Blog URL would depend on its section, so moving a Blog changes all of its URLs, and a site with one section ends up with URLs like `/blogs/blogs/<blog>/`.

## Consequences

- XF 2.3 has no NodeType dev-output type, and `xf_node_type` has no `addon_id` column. So `Setup` inserts the node type row and the `node_type.TaylorJBlogsSection` phrase, then calls `NodeTypeRepository::rebuildNodeTypeCache()`. Uninstall has to delete the section nodes through the entity, moving child nodes up to the parent, and then remove the row. Otherwise the orphaned nodes become invisible on the public side and can't be edited in the ACP.
- The conversion job is the riskiest part of 2.0. It needs a Feature test on seeded threads, reactions and attachments, and a trial upgrade of a real 1.8 database. `checkRequirements()` should warn with the blog and comment counts when upgrading from below `2000031`.
- The mapping table outlives the upgrade, so links to old thread posts can redirect. A later release drops it.
- Members' `message_count` drops when threads are soft-deleted and recovers as comments are created. If the job is interrupted, counts are temporarily low.
- The thread type, ForumType extension, `Service/BlogPost/ThreadCreator`, the thread-creation code in Create, Edit, Approve and `Utils`, and `Job/BlogPostThreadCreation` are all removed.
- Pages that list content from all sections (Author pages, What's New, widgets, search, member stats) must filter by the visitor's section view permission. The `node_ids` option on `LatestBlogPosts`, which currently has no effect, gets used.
- Blog Sections keep denormalized counters and last-post info for the node list, following ADR 0005.
- The upgrade has to generate a handle for every existing Blog and a slug for every existing post, de-duplicating collisions (`-2`, `-3`) and avoiding reserved words and existing section names. Creating a Blog now asks the Author for a handle.
- The catch-all route has to resolve paths cheaply. Section names come from the node cache and handles are an indexed lookup, so a post URL costs at most two queries before the controller runs.
- URL shape is a smaller SEO gain than a few other gaps: there is no sitemap handler (blog posts and Blogs are missing from XenForo's sitemap), no `BlogPosting` structured data, and author pages, paginated lists and the landing page need `noindex` or canonical tags. These belong in 2.0 too.
